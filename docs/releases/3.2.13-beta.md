# SDK 3.2.13-beta

Integrates Sepolia protocol v2.5.5 and subgraph v2.5.13. Mainnet and other-chain
deployment targets and legacy ABIs remain unchanged. This preparation does not
publish the package.

## Routing and deployment

Sepolia's default remains `https://graph.wildcat.finance/sepolia/v2.5.13`. At
verification on 2026-10-02, the release was staged for gateway promotion while
Goldsky finished syncing. Hinterlight was synced and used explicitly for indexed
integration checks. Until promotion, callers can select it without changing the
SDK default:

```ts
import { createSubgraphClient, SupportedChainId } from "@wildcatfi/wildcat-sdk";

const client = createSubgraphClient(
  SupportedChainId.Sepolia,
  "https://graph.hinterlight.net/sepolia/v2.5.13"
);
```

The canonical standard/revolving hooks factories, lens, wrapper factory, and
AccessList provider factory now match the v2.5.5 deployment handoff. Historical
factories remain discoverable through indexed metadata; they do not become
current deployment targets.

All three built-in hooks template classes accept optional `repaymentDate` and
`repaymentPeriod` in deployment previews and transactions. Both are integer Unix
seconds/durations and default to zero, preserving unscheduled deployments. A
scheduled date must be in the future, its deadline must fit `uint32`, and fixed
term repayment cannot precede maturity. A zero repayment period is valid.
Nonzero schedules on older-chain deployment targets return
`DeployMarketStatus.RepaymentTermsUnsupported`; invalid core terms return
`InvalidRepaymentTerms`. Preview validation is static: hook-specific bounds and
transaction-time conditions still apply onchain.

Use `getHooksFactoryDeploymentAbi(chainId, marketKind)` when encoding a preview's
`fn` and `args` directly. It selects the configured target's tuple, including the
two new fields on Sepolia. The existing factory facades do this automatically.
`hooksFactoryV2_5Abi`, `hooksFactoryRevolvingV2_5Abi`, and `wildcatMarketV2_5Abi`
are new exports; legacy ABI exports retain their prior layouts.
`marketLensV2_5Abi` now describes the new configured lens. The deployed
OpenTerm/FixedTerm/PeriodicTerm compositions retain their existing SDK classes;
arbitrary custom policy compositions are not inferred from bytecode.

## App-facing reads and actions

| API | Meaning |
| --- | --- |
| `Market.repaymentDate`, `repaymentPeriod`, `repaymentDeadline`, `defaultedAt` | Optional lifecycle fields. Unsupported historical markets yield `undefined`; supported unscheduled/no-record values stay zero. |
| `Market.hasReachedRepaymentDate`, `isInRepayment`, `hasRecordedDefault` | State at the indexed snapshot or live read, without predicting from the browser clock. A recorded default survives repayment and closure. |
| `Market.liquidity` and existing `maximumDeposit`, `borrowableAssets`, `totalDebts` getters | Full and compact live reads use the lens's exact underlying-token amounts. Deposit/borrow capacity becomes zero in repayment or closure. |
| `Market.recoverableUnderlying`; `MarketAccount.previewRecoverUnderlying()`, `populateRecoverUnderlying()`, `recoverUnderlying()` | Closed-market surplus above all lender and fee liabilities. Recovery requires a borrower account and a live quote, and encodes `rescueTokens(asset)`. Submission verifies signer identity. |
| `getMarketRepaymentHistory(client, { market, block?, fetchPolicy? })` | Optional immutable terms, activation, and default records with transaction/block/log provenance. Effective timestamps remain separate from the transaction that recorded them. |

Refresh before deciding whether to transact. Liquidity values describe accounting
capacity; authorization, sanctions, hooks, token behavior, or a later block may
still prevent the action. `defaultedAt === 0` does not prove that an unwritten
deadline was met. Missing indexed lifecycle records do not establish that either.

`MarketAccount.depositAvailability` now returns `DepositStatus.MarketInRepayment`.
After the repayment date, withdrawal previews follow the core's bypass of hook
admission, including credentials and periodic windows. Market-level sanctions
and balance checks remain enforced by the transaction.

Full market reads also hydrate `registeredWrapper`, periodic withdrawal-window
state and pending APR proposal bounds. A compact refresh clears the window
observation because that tuple does not include it. Effective automatic closure
clears stale periodic APR proposal state. `pendingAprChangeAvailable` indicates
getter support, not the existence of a proposal; use the proposal timestamp to
check for an active proposal.

Hooks instances expose optional `constraints.maximumRepaymentPeriod` and
`maximumRepaymentDateDelay`. The lens's availability flag distinguishes unsupported
legacy constraints from real zero bounds. Template instances and indexed
registrations expose `initCodeHash`; registrations also retain the immutable
commitment record's provenance.

Indexed markets/snapshots include lifecycle event times and `withdrawalRemainder`;
withdrawal batches include `paymentRemainder`. Debt, coverage, and remaining batch
amounts include carry without adding it to ERC-20 supply. Aggregate market carry
can exceed one ray. Live lens tuples provide exact amounts but omit raw carry,
so live refreshes clear the raw remainder while preserving `indexedSnapshot`.
Local projections using a different reserve ratio are estimates when raw carry
is unavailable. Legacy-network withdrawal documents omit the new schema field.

## Consumer migration

The current app passed its baseline type check with 3.2.12-beta. Pointing the same
checkout at this package produced three type errors in two files:

- `src/utils/errors.ts`: add copy for `DepositStatus.MarketInRepayment`.
- `src/utils/formatters.ts`: the generic constraint formatter must handle optional
  bounds. Add the two repayment bounds to its seconds-based keys when displaying
  them; do not divide those durations by 100 as if they were basis points.

Also exclude `MarketInRepayment` from the managed-market “request access” branch
in `src/utils/marketOnboarding.ts`. Add repayment state/history and surplus
recovery UI as needed. No app files were changed as part of this SDK release.
Consumers with exhaustive deployment-status switches must handle the two new
deployment validation values.


uses the explicitly selected Hinterlight endpoint for template registrations.
